# Runtime services

Read this when changing browser preview, auth/login, embedded PTY, the pinned pi runtime, app update checks, subprocess environment, or native runtime dependencies.

- **Browser preview**: `npm run dev:renderer` loads `preview-stub.ts` which stubs `window.pivis` with a demo session and canned responses including streamed agent output.
- **Auth / subprocess env**: API keys are stored in `~/.pi/agent/auth.json` using `proper-lockfile` for mutual exclusion with pi's token-refresh writes. GUI launches recover the user's environment once via `$SHELL -ilc env`; after child creation, the five-second, one-MiB capture is single-flight, uses best-effort process-tree termination, and tears down its local capture pipes at the deadline. `getSubprocessEnv()` combines `process.env` + login-shell env for consistent subprocess PATH across git, PTY, and node/pi spawns. System-Node discovery reuses that environment for a bounded PATH lookup and version probe within one shared five-second budget rather than invoking another login shell. Pi session spawns additionally merge `settings.piEnv` (advanced Settings UI, one `KEY=value` per line; applies on new spawn or `/reload`) after the login-shell env and before Pi-Vis-owned `PIVIS_*` controls. Because importing the SDK does not run Pi's CLI bootstrap, the SDK host explicitly establishes both upstream markers: generic agent attribution `AI_AGENT=pi` and Pi coding-agent detection `PI_CODING_AGENT=true`. Built-in Bash, extensions, and direct Shell Turns inherit both. Atomic writes use tmp+rename and chmod 0600.
- **Login**: `/login` queries the active session's public `ModelRuntime` for provider and interactive method metadata, then dispatches an owner-bound `loginProvider` intent. The SDK host revalidates project trust plus the live provider/method immediately before `ModelRuntime.login()`. Its app-owned interaction surface supports OAuth URLs, device codes, progress/info, text/manual/select prompts, and password-style API-key input. For the pinned Pi headless OpenRouter flow, a preceding authorization URL and its instructions remain available when the same login advances to `manual_code`, so the user can still open the browser while entering a returned code or redirect URL. Prompt values remain short-lived UI responses and never enter Zustand, authority outcomes, replay baselines, or logs. Provider errors are sanitized. Successful runtime login writes through Pi's credential store and triggers the silent model-catalog refresh/readback path. Pi 0.84.2 may throw `CredentialSynchronizationError` after the credential commit; that partial success keeps the secret inside the host, publishes a dedicated “saved, refresh failed” warning, and lets the owner-bound readback/retry path recover instead of falsely reporting that sign-in failed. Runtimes without the public login capability retain the embedded xterm.js terminal fallback.
- **UI response ingress**: Main strict-parses every renderer `ExtensionUiResponse` before registry routing. Response `id` and optional `operationId` are bounded to 128 UTF-8 bytes, text `value` to 64 KiB, and unknown object keys are rejected. Existing owner, renderer-generation, host, epoch, operation, and pending-request checks then fence the parsed response. This same bounded seam carries short-lived API-key and manual-code values without persisting them in renderer state.
- **Model catalog refresh**: Pi 0.84.2 refresh returns `{ aborted, errors }` rather than using rejection alone. A refresh intent completes successfully only when it was not aborted and has no provider errors; the host never clones the provider-keyed `Error` map across IPC. The renderer performs its separate owner-fenced catalog read only after that terminal success, so a partial refresh preserves the prior cache and exposes retry. Public auth/catalog signals and runtime-creation timeouts bound work where Pi supports cancellation.
- **Extension APIs**: Pi 0.84.2 extensions may register display-only Markdown transformers. The renderer batches visible user, assistant, and thinking text through an exact-owner `transform_markdown` read before rendering, while the SDK host keeps the extension functions private and returns only transformed strings. Context includes message type, streaming state, and measured width. Failures fall back to the current text, and transformed output never replaces raw authority events, persisted JSONL, history, or model context. The host also inherits `pi.sendUserMessage(..., { expandPromptTemplates: true })` through the public extension runner; no Pi-Vis command parser emulates template, skill, or command expansion.
- **Pinned pi runtime**: Pi-Vis bundles exact `@earendil-works/pi-coding-agent@0.84.2` and never detects or updates a pi binary on the user's machine—upstream ships breaking SDK changes in patch releases, so the runtime only changes with a Pi-Vis release (audit `docs/compatibility/` first). `src/main/pi/pinned-pi.ts` resolves the bundled `dist/cli.js` plus version. The persisted `settings.piBinaryPath` value is ignored unless the process explicitly sets the test-only `PIVIS_TEST_ALLOW_PI_BINARY_OVERRIDE=1` seam; repository E2E launchers opt in, while packaged verification clears it and proves an existing override cannot displace the bundle. The app never exposes a pi self-update target. The SDK host otherwise uses public Pi imports, with the single exact-version exception in [ADR 0006](../decisions/0006-pinned-llama-private-extension-exception.md): the isolated adapter selects Pi 0.84.2's hidden `llama.cpp` factory from its shipped built-in registry and immediately returns to the public inline-extension and runtime APIs. Pi-Vis extension panels deliberately use the unchanged public `TuiMainScreen` because their content-hugging ANSI replay protocol is not a `TuiAltScreen` viewport. Two packaging constraints (both bit in practice): Electron's patched `fs` makes `existsSync` succeed for paths inside `app.asar`, so the resolver must remap any asar hit to the `app.asar.unpacked` mirror before a child consumes it; and electron-builder re-hoists pi's shrinkwrapped nested `node_modules` to top level at package time, so `electron-builder.yml` asarUnpacks **all** of `node_modules/**` (renderer deps are vite-bundled into `out/`; the packaged `node_modules` exists only for subprocesses/native modules) and the host's `resolvePiDependency` searches ancestor `node_modules` dirs instead of assuming the nested layout. Packaged-app resolution cannot be covered by repository-tree tests—`npm run dist` spawns the unpacked CLI, validates the packaged Pi runtime closure, imports the exact private llama adapter, and runs the packaged PTY/Electron journey.
- **Pi tool defaults**: The SDK host does not pass an explicit built-in tool list to `createAgentSessionFromServices()`, so Pi 0.84.2's global/project `defaultTools` setting owns the initial built-in selection. Pi's public resource/session composition still adds extension and SDK custom tools; selecting defaults must not drop them. Experimental strict schemas for Pi's built-in `read`, `bash`, `edit`, and `write` tools remain an upstream `PI_EXPERIMENTAL=1` behavior rather than a duplicated Pi-Vis schema implementation.
- **Pinned Pi runtime patch**: `scripts/patch-pinned-pi.mjs` applies three narrowly scoped 0.84.2 fixes during `postinstall`: preserve tool-call/result adjacency when extensions record a custom message mid-batch ([#8166](https://github.com/earendil-works/pi/issues/8166)), repair an unterminated JSONL tail before the next `SessionManager` append ([#8345](https://github.com/earendil-works/pi/issues/8345)), and merge indexed native Mistral tool-call chunks even when continuation chunks omit the ID ([#8387](https://github.com/earendil-works/pi/issues/8387)). Exact package version plus pre- and post-patch SHA-256 hashes fail closed on upstream drift; `prebuild` re-verifies the installed bytes, behavioral tests cover every defect, and packaged verification checks the patched hashes in the final app. Remove each patch when a later audited exact pin contains the upstream fix; do not widen this into a generic dependency patcher.
- **Pi extension-package updates**: Separate from the pinned runtime and Pi-Vis app updates. A default-on, non-blocking launch check runs after 3s and respects `extensionUpdateCheckEnabled`; opening Settings also checks when no launch/previous result is cached, while the button always performs a fresh manual check. Main owns the cached status and a single-flight claim, so launch, Settings, and manual callers cannot duplicate one package-manager pass. Results publish through `extensionUpdates.status`, populate Settings with every installed user-scoped npm/git package plus its current/latest version, and add an update-only count to the Settings affordance. Checks use pi's public, best-effort `DefaultPackageManager.checkForAvailableUpdates()` in an environment-isolated worker, then enrich the installed catalog with package metadata and public npm/git commands; unavailable registry/remotes leave the latest version unknown instead of hiding the installed row. The worker creates `SettingsManager` with `projectTrusted: false`, so automatic checks never read or trust project-local package configuration. Mutations invoke the bundled CLI only as `pi update --extensions --no-approve` or `pi update --extension <source> --no-approve`; `--self` and `--all` are intentionally absent because the shipped pi runtime remains pinned. Main serializes mutations, and a timed-out CLI is terminated as a process tree so npm/git descendants cannot outlive the reported operation. IPC invokes are `extensionUpdates.status`, `extensionUpdates.check`, and `extensionUpdates.run`.
- **Pi-Vis app updates**: Separate from extension-package updates and from the pinned pi runtime. `src/main/app-updates.ts` uses Electron's built-in `autoUpdater` only for packaged macOS builds (`app.isPackaged`, `darwin`, not `PIVIS_DISABLE_APP_UPDATES=1`). The feed defaults to `https://update.electronjs.org/rsingapuri/pi-vis/${process.platform}-${process.arch}/${app.getVersion()}` and can be overridden with `PIVIS_APP_UPDATE_FEED_URL` for diagnostics. Background check runs at launch after 5s and respects `appUpdateCheckEnabled`. IPC channels are `appUpdate.status`, `appUpdate.check`, and `appUpdate.install`; events are emitted as `appUpdate.status`. When Squirrel.Mac reports `update-downloaded`, the renderer shows a restart-to-install prompt and calls `autoUpdater.quitAndInstall()` through `appUpdate.install`.
- **Renderer navigation**: BrowserWindow consumes Cmd/Ctrl+R and Cmd/Ctrl+Shift+R at `before-input-event`; Chromium refresh is not a supported lifecycle because it destroys generation-fenced renderer custody while SDK hosts continue running. Session `/reload` remains the explicit runtime reload path.
- **Dependencies**: exact `@homebridge/node-pty-prebuilt-multiarch@0.14.0` (native, externalized from main bundle, asarUnpack in electron-builder) carries one repository-owned install patch: its helper-path rewrites match complete `app.asar` / `node_modules.asar` path components so the plain-Node SDK host's already-unpacked path is not rewritten to `app.asar.unpacked.unpacked`. `postinstall` applies the exact-hunk patch to runtime JS and source, `prebuild` fails on version/content drift, and `verify:packaged-pty` exercises both the unpacked system-Node host resolution and Electron's logical-asar main resolution from the final app. This is a bounded compatibility patch pending migration to a maintained PTY package; do not widen it into a generic dependency patcher. Other dependencies are `@xterm/xterm` + `@xterm/addon-fit` (renderer); `@xterm/xterm` + exact-version `@xterm/addon-serialize` (SDK-host Shell Turn emulation/keyframes); and `proper-lockfile` + `@types/proper-lockfile` (main).
